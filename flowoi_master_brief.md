Единая точка правды по всей работе. Детали по каждой теме — в отдельных ТЗ (ссылки в тексте). Раздел **«Установленные факты»** → скопировать в `CLAUDE.md`, чтобы каждая сессия Claude Code стартовала с него.

## 0. Север и принципы (фундамент, важнее всего)

**Север.** Худший исход продукта — **показать уверенную неверную цифру, по которой человек примет решение** (закупка, цена, реклама, распродажа). Молча-неверная финматематика опаснее тормозов и даже дыр в безопасности. Всё ниже ранжируется по этому.

**Flowoi = «экономист-математик в штате», не ещё один дашборд.**

**3 принципа:**
1. **Зеркало Ozon** — базовые метрики сходятся с кабинетом 1:1, наши фишки слоем сверху. Расхождение базовой метрики = баг, не «наша интерпретация».
2. **Два финансовых контура с переключателем:** «Официальные отчёты Ozon» (истина для бухгалтерии) | «Наша модель» (оперативная по дням). **Никогда не смешивать в одной цифре.**
3. **У каждой метрики описание:** что это, почему такая цифра, по каким дням смотреть, факт это или оценка.

**Рабочие правила (на каждом шаге):**
- Маленькими шагами → проверка вживую → дальше. **«Готово» = юзер подтвердил на flowoi.ru**, не «код написан».
- **Бэкап БД перед каждой миграцией** (`pg_dump` затронутых таблиц).
- **Движок общий по ВСЕМ кабинетам** — `cabinet_id` везде параметр, список кабинетов из БД, не хардкод. Добавили кабинет → он сам в синхре.
- **Не угадывай поля** — подтверждай живым вызовом API / контрольным заказом, особенно раз доки устарели.
- **Source-флаг на каждое число:** факт API / факт XLSX / оценка. Факт и оценку не смешивать.
- Не переименовывать кодовую базу `ozon-pro`. Claude не вводит пароли/ключи, не создаёт аккаунты.
- Сначала план (файлы, зависимости, что сломается) → потом код.

## 1. Установленные факты (НЕ переоткрывать — только сверять) → в CLAUDE.md

**Модель цен (проверена на транзакциях и майском файле Жирафа):**
- `seller_working_price` = **19958 ₽** = поле **`marketing_seller_price`** (НЕ `marketing_price`). От неё считается ВСЁ.
- 33000 — мусор, 51999 — зачёркнутая витрина. В финансы не идут.
- `buyer_visible_price` (после СПП) ≈ 13258 (карта) / 12154 (банк) — **маркетинговый слой, маржу продавца НЕ режет** (СПП за счёт Ozon).
- Комиссия FBO ≈ **41%**, считается от **(Выручка + Баллы за скидки)** — подтверждено файлом.
- «СПП = баллы» — **опровергнуто**.
- Региональную цену API не отдаёт (едина по РФ).
- Себестоимость есть не у всех (активный — Бетонорез GlattFix). Без неё прибыль = «не рассчитана / оценка».

**Формула P&L (выверена на Crema Viva, diff = 0):**
```
seller_revenue   = Выручка + Баллы за скидки + Программы партнёров
прибыль_до_сс    = seller_revenue − все комиссии/услуги
чистая_прибыль   = прибыль_до_сс − себестоимость × (доставлено − возвращено)
```
- **Баллы за скидки — ПРИТОК, не расход.** Не вычитать.
- По магазину за май: выручка продавца ≈ **5,84 млн** (не 3,0 млн голой «Выручки»); прибыль до с/с ≈ **1 993 714 ₽**; Crema Viva ≈ **1 141 687 ₽** (контрольный юнит-тест).

**Реалии Ozon API:**
- `/v1/analytics/data` троттлинг ~**1 запрос/мин** → весь диапазон **одним вызовом**, `dimension:["sku","day"]`, не циклом по дням.
- **Реклама — отдельный Performance API** (другой хост, OAuth, 10 кампаний/отчёт, ~1000 отчётов/сут, отчёт до часа). ДРР только оттуда.
- Bulk-история — Report API (create → poll → download файла).
- `transaction/list` — суммы **на отправление, не на товар** → нужен единый метод разбивки posting→SKU для всех затрат.
- `stock_on_warehouses` даёт `volume` (литры) + остатки по складам (`for_sale/shipped/between_warehouses`) — но **только текущие**, историю копим сами.
- **Займов Ozon.Invest в API НЕТ.** «Financing»-операции = услуги (гибкий график −1.5М, досрочная выплата −1.49М), тело/процент не разбиваются.

## 2. ВЕРНО — корректность денег (P0, тут «врут цифры»)

1. **🔴 Двойной счёт.** `ozon_financing_movements` (397 строк) = зеркало `transactions` (283+114), все `affects_pnl=true` → ~**3 млн ₽ учтены дважды**. Считать эти услуги в P&L/воронке/ДДС **только из `transactions`** по трём operation_type; `financing` выключить из сумм (`affects_pnl=false`, максимум как нерасчётная витрина). НЕ убирать из transactions. Переименовать `principal` → `ozon_services_*` (это не тело займа). → `flowoi_tz_loans.md`
2. **🔴 P&L top-line = `seller_revenue`** (Выручка + Баллы + Партнёры), иначе выручка занижена ~вдвое и маржа в ложном минусе. В UI показывать «Выручка продавца» и «Оплачено покупателем» раздельно. → `flowoi_tz_pnl_and_unit_economy_import.md`
3. **🔴 Хранение — развести источники.** `storage_from_xlsx` (точно) vs отдельная `placement_storage_daily` (факт API, PK по дню → нет двойного счёта при перекрытии окон). P&L через `COALESCE(xlsx, sum(daily))`. **Убрать CASE-костыль.** → `flowoi_tz_storage_split.md`
4. **customer_price** — маркетинговый слой, не финансы. Старые месяцы — из `/v2/finance/realization` (Выручка ÷ кол-во), НЕ через `posting/fbo/get` (лимит 90 дней). Помечать «оценка / средняя за месяц». Проверить значение поля на свежем окне.
5. Возвраты/отмены **≠ продажи**. Деньги — `NUMERIC`, не float. Временные зоны не должны съезжать. Тело займа **≠ себестоимость** (когда займы появятся — отдельный учёт).
6. **Единый метод разбивки posting → SKU** (по доле цены/кол-ву) для всех затрат — иначе per-SKU P&L едет на многотоварных отправлениях.

## 3. БЫСТРО — синхронизация → `flowoi_tz_sync_speedup.md`

Цель: первичный бэкфилл всех кабинетов **1–3 ч**, инкремент — **минуты**. Сейчас 2–3 суток держит **паттерн запросов**, не объём и не сервер.

- **Analytics одним диапазоном** (не циклом по дням) — главный выигрыш.
- **Async** `httpx.AsyncClient` + **семафор на класс эндпоинтов** под его лимит + **backoff с `Retry-After`** (не `sleep(60)`). Кабинеты/эндпоинты параллельно.
- **ARQ + Redis + `sync_state`** (курсор/таймштамп/статус по паре кабинет-эндпоинт) — упавший кусок ретраится сам, без перезапуска всего.
- **Инкремент = скользящее окно** (последние ~14–30 дней) с upsert по статусу/суммам, **НЕ только net-new**: заказы и транзакции **мутируют задним числом** (отмена/возврат/доставка позже, комиссии с лагом). Особенно `transaction/list`. Закрытые дни не перетягивать.
- **Bulk-upsert** (COPY во temp + `INSERT … ON CONFLICT`).
- **Обработка ошибок:** 429 и 5xx — ретрай с backoff; **400/401/403/404 — НЕ ретраить** (чинить запрос/доступ/версию); всё в `sync_state` со статусом и телом ошибки. Это лечит «застревание на ретраях».
- Report API (bulk) и Performance API (реклама) — отдельными треками, задел под Phase 2.

## 5. Storage early warning — фича «не попасть на хранение» → `flowoi_tz_storage_early_warning.md`

Повод: soluna03 за май — хранение −365 792 при выручке 343 286, товар в минусе только из-за хранения.

- **Надёжное ядро (на данных, что есть):** `days_of_inventory = остаток / скорость` — не зависит от тарифных таблиц, высокие дни запаса плохи при любом режиме. Учитывает **подсорт** (товар живёт год, не распродаётся в ноль — даты приёмки партий не нужны).
- **Факт:** `placement_storage_daily` (реальное начисление Ozon).
- **Хрупкое = оценка:** точный ₽-прогноз до начала оплаты (литры × тариф × бесплатный период). Тариф/период **в API не отдаются, дрейфуют** (менялись 5+ раз) → в конфиг, помечать «оценка». Литры — из `stock_on_warehouses.volume`.
- **Два режима:** **A. живой подсорт** → `target_stock = velocity × free_period + buffer`, рекомендация «уменьши/увеличь дозаказ» (НЕ распродажа). **B. мёртвый сток** (скорость упала, дозаказа не будет) → распродажа/вывоз/утилизация по `storage_ratio = projected_storage / remaining_margin`.
- **Два уровня против ложных 🔴:** 🟡 «следить» (оборачиваемость, приблизительно) / 🔴 «действовать» (подтверждено фактом из placement report ИЛИ мёртвый сток).
- **Вывод:** алерты на **ПЕРЕХОД состояния** (не на статус — иначе шум) → лента + **ТГ-бот**, с дедупом. Каждый алерт = **действие + цифра**: «держать ещё месяц = −X₽ / распродать −Y% = −Z₽».
- Инструмент для авто-распродажи 🔴 — новые методы управления акциями (см. ниже).

## 6. Карта данных Ozon — что есть / чего нет

| Нужно | Источник | Надёжность |
|---|---|---|
| Заказы / продажи / возвраты | orders sync | надёжно |
| Выручка продавца | transaction accruals + XLSX | надёжно (с фиксом seller_revenue) |
| Комиссии / логистика / эквайринг | transaction + XLSX per-SKU | надёжно |
| Хранение — итог | transaction | надёжно |
| Хранение — per-SKU | XLSX (точно) / placement daily (факт) / расчёт (оценка) | гибрид + source-флаг |
| СПП / customer_price | realization (Выручка) / XLSX (Баллы) | есть, оценка для старого |
| Остатки по складам + объём (литры) | `stock_on_warehouses` | текущие — да, история — копим сами |
| Цена продавца / индекс / комиссия | `product/info/prices` (`marketing_seller_price`) | надёжно |
| Реклама / ДРР | Performance API | отдельный трек |
| Займы (тело/процент) | **НЕТ в API** | ручной ввод (когда появятся) |
| Бесплатный период / тариф хранения | **НЕТ чистого API** | конфиг, дрейфует |
