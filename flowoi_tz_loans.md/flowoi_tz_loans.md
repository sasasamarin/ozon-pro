# ТЗ: учёт кредитов/займов — тело vs процент (диагностика → модель)

**Главный принцип учёта:** заём — это **движение по балансу, а не доход/расход**.
- **Тело долга** (получил / вернул) — в P&L (прибыль) **НЕ участвует вообще**. Только в ДДС/Cashflow как приток (получение) и отток (погашение).
- **Расход в P&L — только процент** и комиссии за выдачу.
- Если тело свалить в расходы Ozon → прибыль занижена на размер тела, бизнес вечно «в минусе» на ровном месте. Это P0 по северу «не показать неверную цифру».

**Тело займа ≠ себестоимость.** Не смешивать:
- Себестоимость — расход при **продаже** конкретного SKU (в P&L).
- Тело займа — обязательство перед банком, к продаже не привязано (только ДДС).
- Можно купить товар на заёмные деньги → это два независимых факта одновременно (себестоимость в P&L + тело в ДДС), не приравнивать одно к другому, иначе двойной счёт или потеря маржи товара.

| Компонент | P&L | ДДС/Cashflow |
|---|---|---|
| Получение займа (тело) | — | + приток |
| Возврат тела | — | − отток |
| Процент | − расход | − отток |
| Комиссия за выдачу | − расход | − отток |

## ШАГ 1 — Диагностика (СНАЧАЛА, без изменений схемы)

Неизвестно, отдаёт ли Ozon API тело и процент по займу отдельными полями. Под «кредитом» у Ozon три разные сущности, в API выглядят по-разному:
- **A. «Досрочная выплата»** — НЕ заём, а услуга ускоренного вывода своих же денег. В отчёте о начислениях идёт как удержание-услуга (рядом с эквайрингом, Premium Plus). Тела/процента нет, только комиссия → просто статья расхода в P&L.
- **B. Заём для продавца (Ozon.Invest)** — деньги от банка-партнёра, гасишь тело+процент. Часто идёт **мимо** Seller API (напрямую от банка). Вот здесь нужно делить тело/процент.
- **C. Рассрочка покупателя («0-0-6»)** — тебе платят всю сумму сразу, кредитной механики на твоей стороне нет → обычная продажа.

**Что сделать (диагностика, вывод в консоль/лог, ничего не писать в БД):**
1. По `/v3/finance/transaction/list` за период, когда был кредит, собрать **уникальные `operation_type` + `operation_type_name`** со суммами и количеством. Вывести списком.
2. Найти строки, относящиеся к займу/услуге, по названию: «кредит», «заём/займ», «погашение», «Invest», «досрочн», «выплат».
3. Для каждой такой строки распечатать **одну запись целиком, все поля** — увидеть, есть ли отдельно тело и процент, или это одна суммарная строка.
4. Вывод записать в `docs/loans_diagnostic.md`: какие operation_type найдены, относятся ли к телу/проценту, разбивает ли их API.

**Не идти к ШАГУ 2, пока не ясно, что реально отдаёт API.** Не угадывать поля.

## ШАГ 2 — Модель учёта (выбрать ветку по результату ШАГА 1)

### Ветка 1: API даёт займ только суммарной строкой ИЛИ не даёт (банк отдельно) — наиболее вероятно
Тело/процент из API не вытащить → заём вводится **вручную** (как себестоимость).

```sql
CREATE TABLE IF NOT EXISTS loans (
  id           BIGSERIAL PRIMARY KEY,
  cabinet_id   BIGINT NOT NULL,
  lender       TEXT,                      -- банк/партнёр
  principal    NUMERIC(14,2) NOT NULL,    -- тело
  rate_pct     NUMERIC(6,3),              -- ставка годовых
  issued_at    DATE NOT NULL,
  term_months  INT,
  note         TEXT,
  created_at   TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE IF NOT EXISTS loan_payments (
  id           BIGSERIAL PRIMARY KEY,
  loan_id      BIGINT NOT NULL REFERENCES loans(id),
  cabinet_id   BIGINT NOT NULL,
  pay_date     DATE NOT NULL,
  principal_part NUMERIC(14,2) NOT NULL DEFAULT 0,  -- тело → только ДДС
  interest_part  NUMERIC(14,2) NOT NULL DEFAULT 0,  -- процент → P&L
  fee_part       NUMERIC(14,2) NOT NULL DEFAULT 0,  -- комиссия → P&L
  source       TEXT DEFAULT 'manual'                -- manual | ozon_api
);
```
- Юзер заводит договор (сумма, ставка, срок) → Flowoi строит график платежей (аннуитет/диффер.), либо юзер вносит факт платежей.
- **ДДС:** issued (+ principal), каждый платёж (− principal_part − interest_part − fee_part).
- **P&L:** только `interest_part + fee_part` за период. `principal_part` в P&L **не попадает никогда**.

### Ветка 2: API отдаёт «услугу досрочной выплаты» (случай A)
Это не заём — просто статья расхода. Завести operation_type как расходную статью в P&L и ДДС. Никакого разделения тело/процент не нужно. (Возможно, уже падает в transactions — проверить, не задваивается ли.)

### Ветка 3 (если ШАГ 1 вдруг покажет): API реально разбивает тело и процент
Маппить поле тела → `principal_part`, поле процента → `interest_part`, `source='ozon_api'`, дальше та же логика разнесения (тело в ДДС, процент в P&L).

## UI / отчёты
- В ДДС показать блок «Кредиты»: притоки (выдачи) и оттоки (погашения), отдельно тело и процент.
- В P&L строка «Проценты по кредитам» (только процент+комиссия). Тело в P&L **не показывать вообще**.
- Подпись (принцип «откуда цифра»): «тело займа не влияет на прибыль — это возврат долга, видно в ДДС».
- Не называть тело займа себестоимостью.

## Приёмка
- Получение займа не увеличивает прибыль; возврат тела не уменьшает прибыль.
- В P&L по займу попадает только процент+комиссия.
- ДДС показывает полный денежный поток (тело + процент).
- Заём, купленный товар и его себестоимость — три разных факта, не задваиваются.

## Принципы
Сначала диагностика (ШАГ 1) → потом модель. Маленькими шагами, бэкап перед миграцией, сверка после. Сначала план (файлы, зависимости), потом код. `cabinet_id` везде в ключах — движок общий по кабинетам.
