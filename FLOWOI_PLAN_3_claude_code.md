```
КОНТЕКСТ ПРОЕКТА (Flowoi / repo ozon-pro)
Стек: FastAPI + TimescaleDB + React + Shadcn + Recharts, Docker Compose на VPS.
Бренд во фронте — Flowoi; внутренний код (repo/БД/модули) — ozon-pro/ozonpro, НЕ переименовывать.
Принципы: (1) данные = зеркало Ozon, итог сходится 1:1; (2) две фин-модели не смешиваются
(офиц. отчёт ↔ наша оперативка), у каждого числа source-флаг; (3) деньги считает ТОЛЬКО backend.
Источник истины: итог месяца = /v2/finance/realization; дневная динамика = /v3/finance/transaction/list;
дельту между ними показывать строкой, не прятать.

ЗАДАЧА: реализовать раздел «План продаж» (sidebar: Аналитика → План/Факт, код plan-fact).
Работай одним проходом, на все уточняющие вопросы отвечай «да» сам и продолжай.
ПЕРЕД любой миграцией БД — сделай бэкап и оставь дамп. Маленькими шагами, тесты после каждого.

=== 1. БД (миграции, с бэкапом) ===
Создай таблицы:
 sales_plan(id, company_id, scope_type[company|cabinet|category|group|glue|sku], scope_ref,
   metric_code, period_start, period_end, analysis_start, analysis_end,
   base_forecast, target_value, distribution_mode[proportional|manual|seasonal],
   source_pref[operational|official], created_at, updated_at, note, source='user')
 sales_plan_item(id, plan_id, sku, glue_id NULL, analysis_value, share_pct, plan_value, is_locked bool)
 sales_plan_daily(id, plan_item_id, date, plan_value, season_weight)
 plan_kpi(id, plan_id, manager_id, metric_code, target_value, bonus_rule jsonb null)
Склейка (glue): несколько SKU = один товар, история объединяется без двойного счёта.

=== 2. Backend: движок прогноза ===
Эндпоинт forecast(metric, analysis_period, forecast_period):
 - берёт истор. ряд метрики (источник по правилу истины), раскладывает на тренд+сезонность,
 - base_forecast = Σ; модификация цели: mod(d)=forecast(d)*(target/Σforecast), форма кривой сохраняется,
 - возвращает ряды (история/база/модиф) + бейдж надёжности (R²/объём истории).
Сезонность: своя история ≥365дн, иначе fallback на нишу через Ozon Premium API.

=== 3. Backend: универсальный ввод + умный каскад (ЯДРО) ===
План задаётся в любой единице (шт заказов / сумма ₽ / чистая прибыль) на любом scope;
остальные метрики пересчитываются автоматически.
Реализуй ПОЛНЫЙ граф зависимостей:
 показы→CTR→клики→конверсия→заказы→%выкупа→продажи→выручка
 −комиссия−логистика−эквайринг−реклама−возвраты=марж.прибыль; −налог−OPEX=чистая→рентабельность;
 реклама(бюджет)→клики↑→заказы↑; реклама→ДРР↑→маржа↓; продажи→оборачиваемость→потребность в поставке.
Коэффициенты (конверсии, %выкупа, ср.чек, CPC, маржинальность) — из истории КОНКРЕТНОГО товара/кабинета,
не средние. Эластичности — из compute_betas; при низком R² помечать «оценочно».
Эндпоинт simulate_plan_change(metric, delta): пример «+10000 кликов» → +заказы, +выручка,
 ДРР с a% до b%, маржа ±Y, порог окупаемости CPC≤Z. Текстовый вывод причина→сумма→эффект.
Непротиворечивость: сумма по SKU = плану кабинета = общему; конфликт (цель>истор.max) подсвечивать.

=== 4. Backend: распределение ===
По товарам: share_sku = метрика_sku(анализ)/Σ; plan_value = target*share. Ручная правка + lock + ребаланс.
Excel выгрузка/загрузка (импорт с подтверждением). Сброс = вернуть пропорции.
По дням: plan_day(d) = plan_sku * season_weight(d), Σweight=1.

=== 5. Backend: факт + сведение + bridge ===
Факт MTD: дневная кривая из transactions; якорь итога = realization (закрытый месяц).
Незакрытый месяц = transactions + флаг «предварительно». Дельта realization−transactions — отдельной строкой.
Метрики: pro-rata, выполнение% (к темпу и полное), run-rate прогноз, необходимый темп/день, вероятность достижения.
Bridge ΔВыручки = эффект_объёма+эффект_цены+эффект_выкупа+эффект_возвратов (сумма = ΔВыручка).
Ранжирование SKU по вкладу в отклонение.

=== 6. Backend: связь с закупками (МЯГКО) ===
Доступно = остаток + в пути + плановые поставки (со сроками). Если план > доступного —
НЕ блокировать и НЕ резать, вернуть флаг hint 🟡 «нужен товар ~N шт, поставка к DD.MM».

=== 7. Backend: tool-calls для AI ===
 get_plan_fact(scope, period, metric) → {план, факт, прогноз, bridge[], top_sku[], реализуемость, kpi[]}
 simulate_plan_change(metric, delta) → каскадный пересчёт.
AI числа не считает — только из tool-call.

=== 8. Frontend (React+Shadcn+Recharts), вкладки Дашборд|План-Факт|Настройки, внутри Факт|Постановка плана ===
ВКЛАДКА «Постановка плана» (визард 3 шага):
 шаг1 выбор метрики (дефолт Заказы шт+сумма) + период анализа + период прогноза + «Спрогнозировать»;
   карточки «Период анализа» (факт) и «Прогнозируемый период» (редактируемая цель + слайдер);
   график изменения метрики (история/прогноз/модиф.прогноз).
 шаг2 «Результаты»: таблица распределения по товарам (Фото|Артикул продавца|Артикул|Период анализа|Процент|
   Значение плана), Выгрузить/Загрузить Excel, Сбросить, чекбоксы, «Распределить по дням».
 шаг3 «Распределение по дням»: AG-Grid-таблица SKU×недели (01.06…31.08), мини-график в строке, «Сохранить планы».
ВКЛАДКА «Факт» (отслеживание): таблица показателей в 3 срезах День|Накопительно|Месяц, в каждом Факт|План|%,
 группы ФИНАНСЫ/ПРОДВИЖЕНИЕ/ПРОДАЖИ; светофор по %; блок «По всему ассортименту» с переключателем показателя;
 burn-up график (факт vs план pro-rata + прогноз) и bridge-waterfall; клик строки → drill-down.
БЛОК KPI менеджмента: назначение плана сотруднику, карточка план/факт/прогноз/%/светофор, рейтинг,
 мотивация 2 модели (A:% от чистой прибыли | B:бонус за пороги, параметры в bonus_rule).
Фронт НЕ считает деньги — только рендер готовых рядов и отправка параметров.

=== 9. Тесты / приёмка ===
 - суммы по уровням бьются (SKU→кабинет→все);
 - фильтр дат точный (Май=01.05–31.05 без июня);
 - каскад без противоречий;
 - дельта realization↔transactions видна;
 - склад только подсказывает;
 - КОНТРОЛЬ: Stolz Kraft май 2026 общие продажи по офиц.отчёту = 5 557 731 ₽ (API ~5,3М, дельта≈СНГ строкой);
   раздел должен сходиться с отчётом, не с API.
Почини падающие тесты GitHub Actions, не оставляй красными.

Сделай всё за один проход, покажи финальный diff и список изменённых файлов.
```
