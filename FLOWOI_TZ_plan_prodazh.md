# ЧАСТЬ A. АРХИТЕКТУРА РАЗДЕЛА (что вообще внутри)

Раздел состоит из **трёх логических экранов** (вкладки):

| Вкладка | Назначение | Кто пользуется |
|---|---|---|
| **1. Постановка плана** (визард) | Поставить цель: выбрать метрику → проанализировать историю → получить прогноз → подправить цель → распределить по товарам → распределить по дням → сохранить | Владелец / аналитик |
| **2. Факт (отслеживание)** | Следить: таблица Факт vs План vs % в трёх срезах (Сейчас / Прогноз конца периода / План на период) + детализация по ассортименту | Владелец / менеджер ежедневно |
| **3. KPI менеджмента** | Назначить план ответственным, мерить выполнение, мотивация, алерты | Руководитель |

**Главный принцип раздела:** план — это не одна вбитая цифра, а **связанная модель**. Меняешь одну метрику → система пересчитывает зависимые (через юнит-экономику и эластичности) и проверяет реализуемость по остаткам/закупкам.

# ЧАСТЬ B. УНИВЕРСАЛЬНАЯ МЕТРИКА (план по чему угодно)

План ставится по **любой** метрике из единого каталога. Метрика выбирается в шаге 1 визарда (как в дропдауне на скрине).

### B.1 Каталог метрик плана
| Метрика | Тип | Формула / откуда | Источник | План? |
|---|---|---|---|---|
| Клики | трафик | из ad/traffic статистики | transactions/ad | ✅ |
| Клики рекламные | трафик | ad_statistics | Performance API | ✅ |
| Показы (всего) | трафик | *пока недоступно из API — пометка* | — | ⚠️ |
| CTR % | трафик | клики / показы | производная | как ограничение |
| Сумма заказов ₽ | деньги | Σ заказов по дате | posting fbo | ✅ |
| Заказы шт | объём | кол-во заказов | posting fbo | ✅ |
| Продажи (выкуп) шт | объём | заказы × %выкупа | transactions | ✅ |
| Прогноз кол-ва продаж | объём | модель спроса | модель | ✅ |
| Прогноз выручки ₽ | деньги | продажи × ср.цена продавца | модель | ✅ |
| Средний чек ₽ | деньги | выручка / заказы | производная | как ограничение |
| Прогноз маржинальной прибыли ₽ | деньги | выручка − все перем. расходы | P&L-движок | ✅ |
| Прогноз чистой прибыли ₽ | деньги | марж.прибыль − налог − OPEX | P&L-движок | ✅ |
| Итого к перечислению за товар ₽ | деньги | payout из realization | realization | ✅ |
| ДРР от выручки % | эффективн. | расход рекламы / выручка | производная | ✅ (лимит) |
| ROMI / ROI рекламный % | эффективн. | (выручка_рк×маржа − расход_рк)/расход_рк | производная | ✅ |
| Рентабельность % | эффективн. | чистая прибыль / выручка | производная | ✅ |
| Оборачиваемость дн | склад | остаток / средние продажи в день | склад+продажи | как ограничение |

**Правило:** метрики делятся на **целевые** (по ним ставим план: выручка, прибыль, заказы, ROI…) и **производные/ограничители** (CTR, средний чек, оборачиваемость — не ставятся напрямую, а вытекают из связанной модели).

### B.2 База плана — КОЛИЧЕСТВО (штуки), деньги — производные
Физический якорь плана — **количество продаж в штуках на SKU**. Так логичнее, потому что товар привязан к штукам: склад и закупки считаются в штуках. Сначала «сколько штук хочу продать», и уже **от штук** считается «сколько хочу с этого получить»:
```
БАЗА:      план_шт (на SKU)  ← первично, привязка к складу/закупкам
ДЕНЬГИ:    выручка = план_шт × цена_продавца × %выкупа
           марж.прибыль = выручка − комиссия − логистика − эквайринг − реклама − возвраты
           чистая прибыль = марж.прибыль − налог − OPEX
"СКОЛЬКО ПОЛУЧИТЬ"  = настройка ценой / маржой поверх количества
```
- Пользователь **может** задать цель и в деньгах (выручка / чистая прибыль) — для удобства; система переведёт её в штуки (÷ цену / маржу) и дальше работает от штук. Это нужно, чтобы план всегда стыковался со складом и закупками (они в штуках).
- Уровни: конкретный товар → кабинет → все кабинеты. Ввод по SKU суммируется вверх (логика E.1).
- **Метрика по умолчанию — «Заказы в штуках»**; рядом сразу показывается, во что это превращается в деньгах (выручка / прибыль), чтобы видеть «сколько получишь».

# ЧАСТЬ C. ДВИЖОК ПРОГНОЗА (откуда берётся базовая цель)

Принцип: пользователь не должен сам лазить, искать продажи и сводить — движок делает всё на этом экране, прозрачно объясняя «почему такой прогноз».

### C.1 Подсветка доступности данных (перед прогнозом)
Как только выбрана метрика и период анализа — сразу **подсветить, по каким месяцам данные честные**:
- 🟢 есть закрытый отчёт + товар продавался → данные надёжные;
- 🟡 данные есть, но частично (товар появился в середине, мало истории);
- 🔴 нет отчёта / товар не продавался / период «дырявый» → в прогноз не берём или берём с пометкой.
Это страхует от прогноза на «дырах» (нет товара ≠ нет спроса).

### C.2 Две роли истории (свежее окно + годовая база)
```
УРОВЕНЬ И ТРЕНД — из СВЕЖЕГО окна (последние 1–3 мес):
   отражает текущую реальность (поменял дизайн карточки → продажи выросли → так и будет).
   Свежие данные = вес выше.
СЕЗОННОСТЬ — из ГОДОВОЙ базы (прошлый год как график):
   ловит ПОВТОРЯЮЩИЕСЯ ВСПЛЕСКИ спроса (праздники, сезон категории),
   а НЕ путает их с артефактами:
     – просадка из-за отсутствия товара (стокаут) — НЕ сезонность;
     – всплеск/просадка из-за рекламы (пере/недорасход) — НЕ сезонность.
   Очистка: перед извлечением сезонности нормируем ряд на стокаут-дни и
   аномалии рекламы (помечаем и исключаем), чтобы остался чистый сигнал спроса.
```

### C.3 Источники сезонности (комбо, с приоритетом)
1. **Своя годовая история** (если ≥ ~365 дней, очищенная по C.2) — главный источник.
2. **Ozon Premium API** — данные ниши/сезонности.
3. **Сезонность категории «с самого Ozon»** — для товаров без своей истории (fallback).
У каждого источника — `source`-флаг; что использовано, видно пользователю.

### C.4 Сборка прогноза
```
Вход: метрика M, период анализа [A1..A2], период прогноза [F1..F2]
1. level/trend = из свежего окна (взвешенно к сегодня)
2. season(d)   = из очищенной годовой базы (C.2) + Premium/категория (C.3)
3. forecast(d) = level·trend(d) · season(d)     (мультипликативно по сезонному индексу)
   Σ forecast = «Прогнозируемый период» (напр. 4 558 на скрине)
4. Цель пользователя (напр. 4 900): mod(d) = forecast(d) × (Цель/Σforecast) — форма кривой сохраняется
5. График: история | базовый прогноз | модифицированный (зелёный пунктир)
```

### C.5 Объяснение на экране (почему так) + таблицы
Под графиком — блок «почему такой прогноз», человеческим языком + таблицы, чтобы не сводить вручную:
- какие месяцы взяты в свежее окно, какие — в годовую базу;
- какие дни исключены как стокаут/реклама-аномалии (и сколько);
- какой источник сезонности использован (своя/Premium/категория);
- таблица «вклад тренда / вклад сезонности» по периодам;
- бейдж надёжности (R²/объём). Мало истории (<30–90 дней) → «прогноз предварительный».

**Что показываем (скрин 4/5):** «Период анализа» = факт за историю, «Прогнозируемый период» = редактируемая цель, график с тремя зонами + блок-объяснение C.5. Всё на одном экране — лазить никуда не надо.

# ЧАСТЬ D. УМНЫЙ КАСКАД СВЯЗЕЙ (сердце «умности»)

Это то, что отличает Flowoi от «вбей цифру». Когда пользователь меняет одну метрику, система пересчитывает связанные **согласованно**, опираясь на историю и эластичности.

### D.1 Пример пользователя (+10 000 кликов)
```
Δклики = +10 000
 → Δзаказы   = Δклики × конверсия_клик→заказ (из истории товара)
 → Δвыручка  = Δзаказы × средний_чек × %выкупа
 → Δрек.расход = Δклики × средняя_цена_клика (CPC из истории)
 → ДРР_новый = (рек.расход + Δрек.расход) / (выручка + Δвыручка)   → ДРР ↑
 → Δмарж.прибыль = Δвыручка × маржинальность − Δрек.расход
       если ROMI рекламы > 0 → прибыль ↑;  если CPC высокий → прибыль ↓
 → вывод системы: «+10 000 кликов дадут ~+N заказов и +X ₽ выручки,
    но ДРР вырастет с a% до b%, маржа изменится на ±Y ₽.
    Окупается, пока цена клика ≤ Z ₽.»
```

### D.2 Граф зависимостей (что на что влияет)
```
Показы → CTR → Клики → Конверсия → Заказы → %выкупа → Продажи
Цена ↘                                   ↘ Средний чек ↗
Реклама(бюджет) → Клики↑ → Заказы↑ ; Реклама → ДРР↑ → Маржа↓
Продажи → Выручка → −Комиссия −Логистика −Эквайринг −Реклама −Возвраты = Марж.прибыль
Марж.прибыль − Налог − OPEX = Чистая прибыль → Рентабельность
Продажи → расход остатка → Оборачиваемость → потребность в поставке
```

### D.3 Откуда берутся коэффициенты
- Конверсии (клик→заказ, %выкупа), средний чек, CPC, маржинальность — **из истории конкретного товара/кабинета** за период анализа (не средние по больнице).
- Эластичности (показы→карточка β0.885 и пр.) — из движка `compute_betas` (уже есть).
- Везде бейдж надёжности; при слабой связи (низкий R²) — каскад помечается «оценочно».

**Правило непротиворечивости:** после любого изменения сумма по товарам = плану кабинета = общему плану; производные метрики пересобираются, конфликт (напр. «цель по выручке требует среднего чека выше исторического max») подсвечивается.

# ЧАСТЬ E. РАСПРЕДЕЛЕНИЕ ПЛАНА (шаги 2–3 визарда)

### E.1 По товарам / группам / склейкам — СНИЗУ ВВЕРХ (главная логика)
Постановка идёт **bottom-up**: сначала товары, потом план по каждому, потом сумма.
```
ШАГ 1. Выбор кабинета(ов) и товаров (SKU / склейки / группы).
ШАГ 2. План по КАЖДОМУ SKU.
   Стартовое значение = прогноз системы по этому SKU (от его истории+тренда+сезонности),
   пользователь может оставить прогноз или вписать своё.
ШАГ 3. СУММИРОВАНИЕ ВВЕРХ (авто):
   план_кабинета = Σ план_SKU(кабинет)
   план_общий    = Σ план_кабинета
   → пользователь видит итог, собранный из его же товаров.
ШАГ 4. ОЦЕНКА ИТОГА:
   устраивает  → сохраняем как есть;
   не устраивает → правим ОБЩУЮ цифру «общими мазками» (top-down коррекция):
       дельта = новый_общий − текущий_общий
       раскидывается по SKU пропорционально их доле,
       НЕ трогая залоченные строки (is_locked).
```
- **Первичен ввод по SKU и сумма вверх.** Распределение сверху — только вторичная корректировка поверх, по желанию.
- Уровни: **кабинет → категория/группа → склейка → SKU**. Любой уровень редактируем; вверх — авто-сумма, правка сверху — авто-раскидка дельты вниз.
- **Склейка товаров** — несколько SKU/артикулов = один товар (история объединяется, без двойного счёта).
- Ручная правка строки SKU → пересбор суммы вверх; можно «заморозить» строку (lock), чтобы коррекция сверху её не двигала.
- **Выгрузить/Загрузить Excel** — массовый ввод/правка планов по SKU оффлайн, импорт с подтверждением.
- «Сбросить» — вернуть план SKU к прогнозному (стартовому) значению.

### E.2 По дням/неделям прогнозного периода (скрин 7/8)
```
План_sku распределяется по дням периода прогноза по сезонной кривой:
   план_sku_день(d) = план_sku × вес_дня(d),   Σ вес_дня = 1
   вес_дня — из season(d) товара (или равномерно, если истории нет)
```
- Сетка по неделям/дням (01.06, 08.06 … 31.08), значение в ₽/шт на пересечении SKU×период.
- Иконка-график в строке → мини-кривая распределения по дням.
- Кнопка **«Сохранить планы»** → запись в БД (это действие, требующее явного сохранения).

# ЧАСТЬ F. ТРИ КОЛОНКИ ИТОГА + ТАБЛИЦА ОТСЛЕЖИВАНИЯ (вкладка «Факт»)

Главная таблица отслеживания (скрин 1–2), для **каждой метрики** три временных среза, в каждом — Факт / План / %:

| Срез | Что значит |
|---|---|
| **Сейчас (День / MTD)** | Факт на сегодня vs план pro-rata на сегодня |
| **Прогноз на конец периода** | Куда выйдем при текущем темпе vs план на период |
| **План (Месяц/период)** | Полная цель на период |

Группы строк таблицы (как в прототипе):
- **ФИНАНСЫ:** Заказы ₽, Продажи ₽, Средний чек, Отмены ₽, Возвраты ₽, Расходы, Себестоимость, Эквайринг, Комиссия, Логистика, Хранение, Платная приёмка, Штрафы, Прочие удержания, Внешние расходы, Внутр./Внешнее продвижение, ДРР%, Компенсации, К перечислению, Налог, Кредит, **Чистый доход, Рентабельность%**.
- **ПРОДВИЖЕНИЕ:** Показы, Клики, CTR, ROMI рекламный.
- **ПРОДАЖИ:** Заказы шт (+самовыкупы), Продажи шт, Отмены/Возвраты шт, %выкупа, Товаров с движением / без / доля без движений, Оборачиваемость, Доставка до клиента, Индекс локализации, Остаток, Замороженный остаток, Стоимость товара (себес.).
- **ПО ВСЕМУ АССОРТИМЕНТУ:** та же логика в разрезе SKU с переключателем показателя.

Каждая ячейка %: цветовой светофор (🟢≥100 / 🟡 80–99 / 🔴<80 к плану-pro-rata). Клик по строке → drill-down в соответствующий раздел (Продажи/P&L/Реклама).

> **Источник истины напоминание:** «Факт» по продажам/выручке тянем из realization (закрытый месяц) с дневной кривой из transactions; незакрытый месяц = transactions + пометка «предварительно». Дельту realization−transactions показываем строкой.
>
> **Структура выручки (берём за основу, как сводит менеджер по отчётам Ozon):** `Оплачено (брутто) − Возвращено = Выручка (нетто)`. Пример формы свода: 6 004 036 − 240 404 = 5 763 632 ₽. **Конкретные числа не хардкодим — они ещё уточняются;** сверяемся с текущим отчётом по этой структуре, не с заниженным API.

# ЧАСТЬ G. KPI ДЛЯ МЕНЕДЖМЕНТА (умный блок)

Отдельный экран. Превращает план в управляемые цели команды.
- **Назначение:** план (целиком или часть SKU/категорий/кабинета) → ответственному менеджеру (связь с разделом **Команда**).
- **KPI-карточка менеджера:** его план / факт / прогноз / % выполнения / светофор / тренд.
- **Метрики KPI настраиваемые:** объём продаж, выручка, маржа, ДРР-лимит, % выкупа, оборачиваемость — что вешаем на сотрудника.
- **Мотивация (2 модели на выбор руководителя):**
  - **(A) Процент от чистой прибыли** — менеджеру начисляется % от чистой прибыли по его зоне (просто, прозрачно).
  - **(B) Бонус за достижение целей (KPI-пороги)** — бонус привязан к выполнению конкретных порогов: напр. «ДРР ≤ X%», «+N тыс. ₽ выручки», «объём ≥ Y шт», «% выкупа ≥ Z». Можно комбинировать пороги с весами.
  - Модель и параметры (проценты/пороги) задаёт руководитель в `bonus_rule`; система не выдумывает суммы, только считает по заданному правилу.
- **Алерты:** менеджер отстаёт >X% / превысил лимит ДРР / товар встал → уведомление (фаза 2: Telegram).
- **Рейтинг команды** по выполнению.
- **Вердикт по каждому:** причина отставания (из bridge) + рекомендация действия.

# ЧАСТЬ H. СВЯЗЬ С ЗАКУПКАМИ / ОСТАТКАМИ (мягкая подсказка, НЕ блокировка)

Логика планирования первична: пользователь начинает с плана, закупки — потом. Поэтому склад **не мешает** ставить план, а **подсказывает и направляет**.
```
Доступно_к_продаже(SKU, период) =
      текущий_остаток
    + товар_в_пути (отгруженные поставки с ETA в периоде)
    + запланированные_поставки (с учётом срока до кластера)

План можно поставить ЛЮБОЙ. Если план_SKU > Доступно — план НЕ режется и НЕ блокируется,
а строка подсвечивается (цвет/бейдж):
   🟡 «Ок. Под этот план нужен товар: не хватает ~Z шт.
       Чтобы успеть — поставка Z шт с приходом до DD.MM (срок до кластера ~N дней).»
   🟢 «Товара хватает.»
```
- Подсказка — некритичная: не мешает сохранить план, просто информирует.
- Кнопка в подсказке «Создать потребность в поставке» → переход в **Поставки/Остатки** с предзаполненным дефицитом (двунаправленная связь, но по желанию пользователя).
- Учитываем сроки: поставка должна успеть до «дни до out of stock» — это часть текста подсказки, не запрет.
- Цель — направлять к бесперебойности и избегать кассового разрыва, оставляя свободу планировать «на вырост».

# ЧАСТЬ H-bis. ИГРОВОЙ РЕЖИМ / ПРИБОРНАЯ ПАНЕЛЬ (не таблица, а «дожать в зелёную зону»)

Опциональный режим визуализации факта — включается в настройках, **для всех или только для менеджеров**. Привязка — к **кабинету / товару / группе товаров** (менеджеры необязательны).
- **Спидометр выполнения:** стрелка = % к цели по темпу. Зоны 🔴 отстаём → 🟡 почти → 🟢 в цель → 🔵 перевыполнение. Цвет и подпись статуса меняются вживую.
- **Темп-слайдер:** «если держать N шт/день» → стрелка и прогноз конца периода пересчитываются; подсказка «нужно X/день, чтобы попасть».
- **Уровни:** растут от стабильности в плане (Прокол → Разгон → В цель → Газ в пол) + прогресс-бар до следующего.
- **Серия (стрик):** дней подряд в зелёной зоне; гаснет при выпадении.
- **Рейтинг (опц., если включены менеджеры):** бары по % выполнения, окрашены по зоне, с местами. Это KPI-блок в игровом виде.
- **Фаза 2:** ачивки/бейджи (перевыполнил 3 мес, удержал ДРР<порога), недельные челленджи, командный общий прогресс-бар, алерты «выпал из топ-3».
- Числа — те же, что в обычной таблице (один источник), просто другой способ показать. Не выдумывать.

# ЧАСТЬ I. 25 ПУНКТОВ (сводно, с учётом A–H)

**1. Название:** План продаж (План/Факт).
**2. Главная задача:** ставить цель по любой метрике, прогнозировать реалистичный план от истории, видеть разрыв план/факт/прогноз, понимать причины и что сделать, проверять реализуемость по складу.
**3. Боль:** цель «в голове»; план без связи с рекламой/закупками; не видно вовремя отставание; нельзя обещать больше, чем есть товара.
**4. Главные вопросы:** Сколько ставим и реально ли? Иду ли к цели? Куда выйду при текущем темпе? Что меняет +N кликов/рублей? Хватит ли товара? Кто из команды отстаёт и почему?
**5. Данные:** план (ввод), факт по метрикам, история для прогноза, эластичности/конверсии, остатки+поставки, оргструктура (менеджеры).
**6. Источники:** realization (истина итога) · transactions (дневная динамика) · posting fbo (заказы) · ad/Performance (реклама) · P&L-движок (прибыль) · sales_plan (ввод) · supply/stock (реализуемость) · Ozon Premium (сезонность fallback).
**7. Проверка:** зеркало с ЛК; сверка realization↔transactions с подписанной дельтой; сумма SKU = кабинету = общему; флаг неполноты себестоимости; «предварительно» для незакрытого месяца.
**8. Показатели:** План / Факт MTD / План pro-rata / Вып.% / Прогноз конца периода / Необходимый темп / Вероятность достижения / Bridge факторов / KPI по менеджерам.
**9. Формулы:** см. Часть C (прогноз), D (каскад), F (pro-rata, %), H (реализуемость). Доп.:
```
Вып.%(к темпу) = ФактMTD / Планpro-rata × 100
Необх.темп/день = (План − ФактMTD) / осталось_дней
Прогноз = (ФактMTD/прошло_дней)×всего_дней  ИЛИ ФактMTD + Σmod(d) по остатку
```
**10. Логика расчёта:** прогноз от истории → модификация цели → каскад связей → распределение товар/день → проверка по складу → сверка факта → bridge причин → рекомендации.
**11. Графики:** burn-up (факт vs план pro-rata + прогноз), кривая прогноза (история/база/модиф), bridge waterfall, мини-кривые по SKU, светофор-heatmap по ассортименту.
**12. Таблицы:** (а) постановка-распределение по товарам; (б) распределение по дням; (в) отслеживание Факт/План/% × День/Накопит./Месяц по группам ФИНАНСЫ/ПРОДВИЖЕНИЕ/ПРОДАЖИ; (г) по ассортименту; (д) KPI по менеджерам.
**13. Фильтры:** период анализа, период прогноза, метрика, scope (кабинет/категория/склейка/SKU), источник факта (офиц./наша), режим распределения (пропорц./ручной/сезонный).
**14. Предупреждения:** отставание >15%; прогноз < плана; ДРР > лимита; план выше доступного товара (🟡 мягкая подсказка «нужен товар/поставка», не блок); цель > исторического max (нереалистично); истории мало (низкая уверенность); незакрытый месяц.
**15. Рекомендации:** причина → сумма → действие → эффект. Напр.: «Отстаёте −420 000 ₽; главная причина — цена (−260к) и возвраты по Жирафу (−90к). Нужен темп 32/день. Действия: выйти из акции по X (+8% цены); усилить рекламу Y (запас ДРР); по Z дефицит — поставка 300 шт к 14.07.»
**16. Действия пользователя:** выбрать метрику/период; задать цель слайдером; править распределение; выгрузить/загрузить Excel; сохранить план; назначить KPI менеджеру; принять рекомендацию (переход в Рекламу/Цены/Поставки); сбросить.
**17. Крайние случаи:** план не задан (пустое + CTA); мало истории; realization≠ЛК (бейдж); SKU перенесён между кабинетами; несколько SKU=1 товар (склейка); лаг возвратов; сумма уровней не бьётся; план превышает склад.
**18. Связи:** Продажи (факт/drill), P&L (прибыль, bridge-расходы), Реклама (ДРР/каскад), Цены/Акции (цена/чек), Возвраты, **Поставки/Остатки (реализуемость ↔ потребность)**, Сезонность (веса), Команда (KPI), AI-аналитик (готовый bridge+рекомендации).
**19. Первый экран:** крупно Вып.% + светофор + Прогноз vs Цель + строка-вердикт; ниже burn-up.
**20. Детальный просмотр:** bridge с числами, таблица по SKU с вкладом, дневная таблица факт/план/темп, KPI по менеджерам, переключатели.
**21. Авто-инсайты:** доминирующий фактор отставания; SKU-киллеры; «план нереалистичен»; «реклама вне лимита, но тянет именно она»; «опережение за счёт акции — упадёт маржа»; «дефицит товара под план».
**22. Хранить в БД:** см. Часть J.
**23. Backend считает:** прогноз, каскад связей, распределения, сведение источников, pro-rata/%/темп/прогноз, bridge, проверку реализуемости, тексты рекомендаций, KPI-агрегаты. Все деньги — на backend.
**24. Frontend:** отрисовка графиков/таблиц из готовых рядов, фильтры/слайдеры (шлют параметры), Excel выгрузка/загрузка UI, форматирование, тултипы-описания. Без финрасчётов.
**25. Для AI:** tool-call `get_plan_fact(scope, period, metric)` → {план, факт, прогноз, bridge[], top_sku[], реализуемость, kpi[]}; `simulate_plan_change(metric, delta)` → каскадный пересчёт. AI берёт числа только из tool-call, не считает; раздел = вход для ролей «Что видим» / «Что сделать».

# ЧАСТЬ K. UX-ПОТОК (мануал — как этим пользоваться)

# РЕШЕНИЯ (зафиксированы, готово к Claude Code)
1. **Каскад связей** — делаем **полный граф** D.2 (Flowoi = аналитический мозг, не урезаем).
2. **Сезонность для распределения по дням** — своя история + **общий тренд ниши из Ozon Premium API**; при нехватке своей истории — fallback на нишу.
3. **KPI-мотивация** — две модели на выбор руководителя: **(A) % от чистой прибыли** или **(B) бонус за достижение порогов** (ДРР ≤ X, +N ₽, объём, % выкупа). Параметры — в `bonus_rule`.
4. **Реализуемость по складу** — **только подсказывать и направлять**, не блокировать и не резать план.
5. **Метрика по умолчанию** — **Заказы (одновременно шт и сумма ₽)**. Универсальный ввод: можно ставить в шт заказов / в сумме заказов / в чистой прибыли — на товар / кабинет / все кабинеты, остальное система пересчитывает сама.
